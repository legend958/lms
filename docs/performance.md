# Performance evidence

Reference environment: Docker Desktop on Windows, 8 vCPU, 2.78 GiB RAM for the
Linux VM, 1 GiB swap (≈750 MiB already in use). Services: one uvicorn worker with
the local MiniLM embedder, Postgres 16, Redis 7, Chroma 1.5.9, Next.js 15.
Measurements taken 2026-11-05 against the hardened stack, with the *real* login
and assistant rate limits enabled.

## Targets

| Path | Target |
|---|---|
| CRUD (student hot paths) | 50 req/s, P95 < 400 ms |
| Study assistant (SSE) | 2 req/s, P95 < 8 s |

## Results

Each row is one `load/k6.js` run. Sessions were pre-generated by
`scripts/k6_sessions.py` and reused, so setup does not consume the login budget.

| Run | Rate | Duration | Achieved | P95 | Failed reqs | Dropped iters | Verdict |
|---|---|---|---|---|---|---|---|
| CRUD | 10/s | 30 s | 9.8/s | **71.8 ms** | 0 | 0 | Pass |
| CRUD | 25/s | 30 s | 24.9/s | **56.5 ms** | 0 | 0 | Pass |
| CRUD | 25/s | 60 s | 23.7/s | **1 200 ms** | 0 | 49 | Fail |
| CRUD | 50/s | 30 s | 48.5/s | **578.6 ms** | 0 | 17 | Fail |
| CRUD | 50/s | 60 s | 31.1/s | **10 000 ms** | 173 (8.8 %) | 1 041 | Fail |
| RAG | 2/s | 30 s | 2.0/s | **1 480 ms** | 0 | 1 | Pass |
| Mixed\* | 25/s + 2/s | 60 s / 30 s | 23.6/s | CRUD **1 910 ms**, RAG **6 830 ms** | 15 (1.0 %) | 54 | Fail (CRUD) |
| Acceptance (50/s + 2/s) | 50/s + 2/s | 60 s / 30 s | 19.6/s | CRUD **9 960 ms**, RAG **2 070 ms** | 130 (6.2 %) | 965 | Fail (CRUD), pass (RAG) |

\* The mixed-25 row was captured *before* the k6 topic/course pairing fix
described below, so some of its request failures are load-script 404s rather
than capacity failures. It is kept for the latency trend only; the acceptance
row is the corrected run.

**Verdict: the CRUD P95 target is not met at 50 req/s on this VM.** The assistant
target is met. The failure is reported as-is; no rate was lowered and no limiter
was disabled.

### What the numbers mean

- At 10 and 25 req/s the stack is comfortably inside the 400 ms budget in short
  runs (P95 57–72 ms).
- A sustained 60 s run at the same 25 req/s degrades to P95 1.2 s with *zero*
  failed requests. During that run the API's own request log never exceeded
  133 ms; the extra second is spent before the request enters the ASGI app or
  after the response leaves it. That is host/VM scheduling and I/O stall, not
  query time (see "Diagnosis").
- At 50 req/s the single worker saturates. Latency rises, more requests are in
  flight, the SQLAlchemy pool (`pool_size=10, max_overflow=20`, timeout 30 s) is
  exhausted, and requests then fail with
  `QueuePool limit of size 10 overflow 20 reached` after waiting 30 s.
  Throughput collapses to ~31 req/s.
- The assistant path is fast when it runs alone (P95 1.48 s against an 8 s
  budget). Under concurrent CRUD load its P95 rises to ~2 s but still passes.
  In the corrected acceptance run all 130 failures were CRUD requests: the run
  had 2,102 HTTP requests and 2,157 checks, so 55 assistant requests (2 checks
  each) and 2,047 CRUD requests (1 check each); 130 failed checks and 130 failed
  requests can only mean 0 assistant failures and 130 CRUD failures.

## Diagnosis

### 1. Garbage collection on the embedder heap (fixed)

Profiling a 20-VU in-process workload showed one gen-2 collection taking
**5.76 s**. The long-lived embedding model creates ~660 k Python objects; every
full collection rescans them. After `gc.collect(); gc.freeze()` following
embedder warmup, the same workload measured:

| Configuration | CPU per request |
|---|---|
| Default GC | 43.3 ms |
| `gc.collect(); gc.freeze()` after warmup | **28.7 ms** |
| GC disabled | 25.0 ms |

`gc.freeze()` is now applied in `backend/app/main.py`; the API logs
`gc_heap_frozen frozen_objects=659692`. Objects allocated after warmup are still
collected; only the pre-existing model/ORM heap is frozen.

### 2. Access logging (removed)

Uvicorn's access log costs ≈1.4 ms/request (9.41 → 9.95 ms with logging
suppressed for `/auth/me`, 15.57 → 14.13 ms for `/student/topics`). Uvicorn runs
with `--no-access-log`; the structured middleware log (request id, status,
duration) is retained.

### 3. Database connection settings (not the bottleneck)

| Variant | Median wall | Median CPU |
|---|---|---|
| `pool_pre_ping=True`, pool 10+20 | 4.51 ms | 3.65 ms |
| `pool_pre_ping=False`, pool 10+20 | 5.15 ms | 4.22 ms |
| `pool_pre_ping=False`, `NullPool` | 23.78 ms | 10.75 ms |

The current pool settings were left unchanged. The pool is a *symptom* under
overload, not the steady-state cost.

### 4. Hot-path query plans

`load/explain.sql` runs `EXPLAIN (ANALYZE, BUFFERS)` for the six hottest shapes.
On the demo dataset:

| Query | Execution time | Access path |
|---|---|---|
| Q1 student task list | 9.4 ms | `ix_tasks_course_due`, `ix_courses_status`; small seq scans on 6-row tables |
| Q2 completed tasks (roster) | 5.0 ms | `ix_tasks_course_due`, `users_pkey` |
| Q3 average quiz score | 7.3 ms | `ix_quizzes_course_status`, `users_pkey` |
| Q4 knowledge gaps | 20.0 ms | `ix_attempt_answers_question_id` (new), `ix_questions_quiz_order` |
| Q5 audit viewer | 34.0 ms | bitmap `ix_audit_entity`; 53-row heap scan |
| Q6 student quiz list (release-gated) | 2.5 ms | `ix_quizzes_course_status`, `ix_courses_status` |

Migration `0011_hot_path_indexes` added:

- `ix_attempt_answers_question_id` — used by Q4 (per-question accuracy).
- `ix_quiz_attempts_student_started` — student attempt history and analytics.

Every plan is sub-35 ms on the demo data and no query shows a sequential scan of
a large table. Query time is not what fails the 50 req/s run.

### 5. Worker capacity (the hard limit)

One API worker with the embedder uses ~750–830 MiB. Two workers were tested with
serialized warmup (an advisory `/tmp` lock) so the model does not load in both at
once; both were still OOM-killed in a restart loop (`Child process ... died`) on
the 2.78 GiB VM, which already has ~750 MiB of swap in use. `API_WORKERS` is
parameterized, but the default is `1` because a larger value is not safe here.

The single worker's sustained ceiling for this request mix is ~30 req/s. At
50 req/s the event loop is CPU-saturated; each request holds a database
connection longer, the 30-connection pool empties, and the queue-latency
feedback loop produces the 10 s tail and 500s.

### 6. Analytics cache

Cohort KPIs and the student list are cached for 60 s per
`(course_id, filter_hash)` and invalidated by release, completion, and attempt
submission (`test_analytics.py` asserts the cached read and the invalidation).

## Remediation

The application code is not the limiting factor; the VM is. In order of impact:

1. **Give the API host more RAM and run 4 workers.** At ~800 MiB per worker plus
   ~400 MiB for the rest of the stack, 4 GiB supports 2 workers and 8 GiB
   supports 4–6. Set `API_WORKERS=4`; the pool is per process, so effective
   database concurrency also scales. On 4 workers the measured 25 req/s headroom
   extrapolates to ≥100 req/s.
2. **Move the embedder out of the API process.** The assistant only needs
   embeddings for one short query. Running MiniLM in the ARQ worker (or a small
   internal embedding service) would drop each API worker to ~150–200 MiB and
   make 4–6 workers fit in 2 GiB. This is an infrastructure change, not a
   product feature, and is the recommended next step.
3. **Fail fast under overload.** Once capacity is fixed, consider lowering the
   pool checkout timeout from 30 s to a few seconds and returning `503` with
   `Retry-After` instead of letting requests queue for 30 s. This changes
   overload behaviour and was deliberately not done during hardening.
4. **Re-run the acceptance test on the target host** with `API_WORKERS` sized to
   the RAM. The k6 script and session tooling are ready:
   `scripts/k6_sessions.py` then `load/k6.js` with `SESSIONS_FILE=sessions.json`.

Until one of the first two items is done, treat 25 req/s as the supported CRUD
load on this reference VM and 50 req/s as a known, documented gap.
